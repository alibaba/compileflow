# 测试指南

测试用于验证文档声明的行为。优先选择能够证明规则的最小测试层级；只有规则跨越模块或持久化边界时，才增加更高层级的测试。

## 测试层级

| 层级       | 范围                                   | 典型用途                                              |
| ---------- | -------------------------------------- | ----------------------------------------------------- |
| 单元测试   | 单个类或纯规则                         | 解析、校验、路由、状态转换和错误映射。                |
| 模块集成   | 一个 Maven 模块及其依赖                | Spring 组装、生成代码、资源生命周期和 Provider 行为。 |
| 存储契约   | 一个受支持的真实数据库实现             | 事务、数据库迁移、锁、租约和恢复语义。                |
| 跨模块集成 | Engine、Deploy、Durable 或 Server 组合 | 公开工作流和精确版本归因。                            |
| Workbench  | pnpm workspace                         | TypeScript、契约、UI 和浏览器行为。                   |

测试结果必须可重复。不要依赖执行顺序、开发者主目录、默认时区、网络可用性或其他测试遗留的静态状态。

## Java 测试

测试应放在生产模块旁边；公开行为应通过公开契约验证。测试名应表达它证明的规则。回归测试应包含此前失败的最小输入。

对于并发和生命周期代码：

- 使用 latch、barrier 或可控时钟，不使用任意时长的 sleep；
- 明确断言资源归属、取消、隔离令牌和关闭行为；
- 关闭执行器、类加载器、数据库连接和子进程；
- 同时验证成功路径和失败时拒绝继续的路径。

生成 Java 代码的测试应验证语义输出和执行行为，不要依赖容易变化的格式细节。只有生成结构本身属于契约时，才使用源码快照。

## 持久化测试

数据库迁移和事务行为必须在功能涉及的每一种受支持数据库上验证。模块声明支持时，覆盖 PostgreSQL 16、17、18 和 MySQL 8.4。H2 仅用于测试，不能证明生产数据库兼容性。

持久化变更至少覆盖：

1. 空数据库结构创建和迁移校验；
2. 提交与回滚；
3. 并发领取或 compare-and-set 状态转换；
4. 适用时的重启、租约过期和恢复；
5. 明确的错误或死信处理。

存储实现必须通过通用的 Store 测试套件。已经发布的迁移脚本不得原地修改。

## Spring 与 Server 测试

使用范围尽可能小的 Spring 上下文。验证必需组件存在、未完整选择存储实现时启动失败，以及未启用的可选功能不会引入数据库依赖。

服务端接口测试应覆盖请求校验、认证模式、Problem Detail 响应、OpenAPI 结构、持久化结果和幂等性。Workbench Server `/api/**` 是同版本配套契约，变更时必须同步更新 Controller 类型、OpenAPI 快照、生成的前端类型、运行时校验和测试。

## 定向命令

运行一个测试类：

```bash
./mvnw -pl <module> -Dtest=<TestClass> test
```

同时构建依赖模块：

```bash
./mvnw -pl <module> -am -DskipTests compile
```

运行聚焦的集成测试：

```bash
./mvnw -pl compileflow-integration-tests -am -Dtest=<TestClass> -Dsurefire.failIfNoSpecifiedTests=false test
```

运行仓库文档和架构门禁：

```bash
python3 scripts/check_internal_links.py
python3 scripts/check_bilingual_parity.py
python3 scripts/check_architecture_boundaries.py
python3 scripts/check_spec_impl_parity.py
git diff --check
```

在 `compileflow-workbench` 中使用 `package.json` 定义的脚本运行 Workbench 检查，通常包括：

```bash
pnpm type-check
pnpm test
pnpm build
```

只有浏览器功能受影响时才运行对应的 Playwright 命令。服务端和浏览器目标必须显式配置；目标不可用时应失败，不能静默跳过应执行的测试。

## 可执行 Server 冒烟测试

当变更影响打包、配置、数据库迁移、认证或跨模块组装时，应使用受支持数据库运行打包后的可执行 JAR。至少验证启动、数据库结构校验、一次认证请求、一次流程执行、启用 Deploy 后的一次部署操作和正常关闭。单元测试或只使用 H2 的测试不足以覆盖这些场景。

## 失败诊断

不稳定测试应视为缺陷信号。保留随机种子、输入、线程状态、数据库日志和相关配置，判断问题来自并发竞态、资源泄漏、环境依赖还是测试本身不确定。修复根因并增加可重复的回归测试，不要通过延长等待、弱化断言或无限重试掩盖问题。

## 提交前清单

- 新行为有测试，修复缺陷有回归测试；
- 测试在合适的最小层级证明公开契约；
- 并发和时间行为使用确定性协调；
- 持久化变更已在所有相关的受支持数据库上验证；
- API、配置、REST、数据库结构、传输协议和生成客户端的变更已覆盖对应契约层；
- 已运行定向测试和仓库门禁；
- 工作区没有遗留构建产物。
