# 部署与运行时运维

本文提供 Deploy 和 Workbench Server 的运维清单。发布操作见[热部署](hot-deploy.md)，持久化流程恢复见[Durable 运维手册](durable-operations-runbook.md)。

## 变更前

- 确认目标命名空间、流程编码、别名、确定版本和当前路由修订号；
- 确认内容摘要和不可变版本身份；
- 确认数据库健康、迁移状态、Outbox 状态、投影存储访问权限和运行时容量；
- 在切流前定义观察窗口、最小灰度样本和回滚权限；
- 不要将 API 密钥、路由键、载荷变量和租约令牌写入日志或工单。

## 发布与切流

1. 校验流程定义，执行适用的预检和发布测试；
2. 发布新的不可变版本；同一身份不能复用到不同内容；
3. 读取当前别名路由，将修订号作为并发前置条件提交；
4. 使用稳定的幂等键创建全量或灰度发布；
5. 验证控制面提交、Outbox 投递、本地就绪状态和一次真实执行。

在 `DISTRIBUTED` 拓扑中，命令成功只表示控制面事务已经完成，不代表所有执行节点都已就绪。执行节点使用最近一次原子发布且本地就绪的修订号；没有有效修订号时，别名解析失败并拒绝执行。

灰度权重使用 `1..9999` 的整数基点。应在预先确定的观察窗口内结合技术和业务指标评估；内置健康接口只提供只读信息，不会自动全量切换或中止。`412 Precondition Failed` 表示并发状态已过期，应重新读取；`409 Conflict` 表示存在需要人工处理的语义冲突。

## 中止与回滚

中止进行中的灰度：停止调整权重，使用当前发布修订号和明确原因提交 `AbortRolloutCommand`，再确认创建灰度时记录的基线路由已恢复。

回滚已完成部署：选择仍对应当前路由修订号且保留基线的已完成发布，使用新的幂等键提交回滚并验证收敛。已有发布记录保持不变。

## 异步调用健康

使用 `/api/async-invocations/health` 作为队列快照：

- ready 表示等待执行容量，delayed 表示尚未到重试时间；
- 正在本地运行和已经分发的数据属于当前节点；已持久化的排队、死信和租约过期数据由所有节点共享；
- `degraded` 表示存在死信或过期的运行租约，不等于已经违反 SLO；
- 通过调用 ID 关联尝试记录、追踪信息、实际版本、别名修订号和运行时诊断；
- 只有修复流程模型、制品、容量或依赖问题后，才能重新入队。

运行中的调用在租约过期后恢复；隔离令牌机制会拒绝原执行节点迟到的完成结果。不要直接修改队列记录，也不要通过缩短租约强制恢复。

## 事故检查

### 发布被拒绝

检查 `DeploymentException` 的错误码和请求 ID，再检查版本身份、模型类型、UTF-8 大小、操作者和摘要断言。使用预检定位模型问题；流程内容变化后必须使用新的版本身份。

### Outbox 或投影堆积

检查部署健康状态，区分状态不可用与可信的零计数。分别检查等待处理、正在处理、领取过期、重试和死信记录。确认凭据、写入延迟和投影存储的比较并设置行为后再重试。重复投递是正常情况，内容冲突则必须处理。

### 运行时安装失败

通过 `DeploymentRuntime.snapshot()` 检查精确版本和退避原因，确认制品、摘要、读取权限、编译资源和执行器容量。不要绕过本地就绪检查，也不要回退到无版本流程定义。

### 重启

重启后依次确认数据库结构校验、Outbox 投递、对账、路由收敛和过期租约恢复，再通过别名执行一次流程。在受保护的日志或诊断信息中检查实际版本和路由修订号；内置指标标签不会记录这些高基数身份。

## 日常检查

定期检查发布冲突、路由和发布修订号、Outbox 积压、运行时失败、异步死信、过期租约和收敛时间。按照明确的引用和回滚策略保留版本；仍被路由、保留的流程实例或恢复窗口引用的版本不得删除。
