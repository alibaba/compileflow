# API 设计原则

## 目的

CompileFlow 根据操作职责选择 API 形态。公开接口应尽量小而稳定：必需信息直接可见，无效请求难以构造，长期存在的概念只有一种规范表达。

## 按职责选择形态

| 职责                           | 形态                                | 示例                                                                  |
| ------------------------------ | ----------------------------------- | --------------------------------------------------------------------- |
| 高频嵌入式应用调用             | `verb(required arguments, Options)` | `ProcessEngine.execute`、`DurableProcessEngine.start`、`completeWait` |
| 需要审计或修订号检查的控制操作 | `verb(Command)`                     | Deploy 发布命令；Durable 暂停、恢复与裁决命令                         |
| 包含多个过滤或分页字段的读取   | `verb(Query)`                       | 流程实例、Timeline、Outbox、版本和 Rollout 查询                       |

只有在需要表达明确契约时，才将简单的应用调用包装成命令对象。

## 原则

1. 根据操作职责选择方法形态，不追求无关 API 之间的外观统一。
2. 如果使用不同类型或重载就能阻止无效请求，应优先在类型层完成约束。例如，精确版本准入和别名
   准入不能先接受通用 `ProcessRef`，再到运行时拒绝。
3. 必需的领域信息直接作为方法参数；可选的单次调用行为放入 `Options`。不要在其中堆积无关字段。
4. `Command` 只用于需要审计、特权或修订号检查的变更。`execute`、`start`、`completeWait`、`cancel` 等高频嵌入式调用，
   没有明确语义需要时不包装为 `Command`。
5. 读取操作包含多个过滤条件、排序、边界或游标时，使用不可变 `Query`。
6. 规范的身份类型应端到端传递。稳定 API 使用 `ProcessRef.Version` 和 `ProcessRef.Alias`，不要反复拆成字符串。
7. 能力令牌和游标对应用是不透明值。应用可以传递其标量值，但不能依赖存储键、内部流程实例或元素身份、
   排序实现等细节。
8. 绝对时间使用 `Instant`；时间长度使用 `Duration`，或在字段名中明确单位。
9. 复杂公开视图需要保留演进空间。优先使用 Builder 或符合职责的构造入口，避免参数过多的位置构造器。
10. Java API、线协议和数据库架构是相互独立的契约。JSON 字符串或 SQL `bigint` 不能反向决定公开 Java 领域类型。
11. JVM `public` 可见性不代表产品支持。实现指标、仓储记录、适配器和装配代码只有被支持面规范明确列出时，
    才属于支持面。
12. 只有当新类型提供必要能力，或能阻止一类有意义的无效请求时，才加入公共 API。

## 稳定的身份与准入规则

- `ProcessDefinition` 提供明确的 `Inline` 与 `Classpath` 来源；`ProcessRef.Version` 与
  `ProcessRef.Alias` 是两种已发布引用。
- `ProcessExecution` 报告实际执行的流程身份与可选的精确已发布 `ProcessRef.Version`。
- 即时执行接受 `ProcessEngine` 路由所支持的引用形态。
- Durable 精确准入接受 `ProcessRef.Version`；别名准入接受 `ProcessRef.Alias` 并只解析一次。两条路径最终都物化相同的
  精确流程语义。版本可以保留为准入归因，但恢复只使用已存储的流程 ID，不再通过版本或别名路由。
- 别名是可变的 Deploy 控制面状态，不是 Durable 恢复身份。
- Deploy 领域制品位于 `deploy.api.artifact`；协议解析器、载荷和键位于 `deploy.protocol`。

## 身份与所有权

以下分类用于说明各类身份的职责，并不对应五个公共类型。

| 分类       | 事实与所有者                                                                    | 不应替代的概念                                       |
| ---------- | ------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 语义身份   | `ProcessDefinition` 声明模型类型与流程编码；解析后的快照固定源字节              | 不能由引擎配置补全，也不能把可变资源路径当作内容身份 |
| 准入身份   | `ProcessRef.Version` 或 `ProcessRef.Alias` 标识请求的发布目标；准入负责解析路由 | Durable 恢复身份                                     |
| 运行时身份 | 引擎本地可执行实现由语义内容、构造管线与类加载器范围共同确定                    | 可跨节点传输的数据库键                               |
| 恢复身份   | Durable 存储保存流程实例的精确流程、延续状态与冻结的调用目标                    | 当前别名路由、版本来源或本地缓存                     |
| 运维身份   | 持久化控制状态、修订号与租约权威约束运维和工作节点变更                          | 不能仅凭流程编码、调用归因或诊断用工作节点名称授权   |

共享词汇不等于共享聚合配置所有权。生命周期根拥有构造配置；协作者只接收实际使用的能力和值。框架适配层负责属性绑定
与生命周期时序，不建立第二个运行时所有者。

重复表达不等于重复权威。数据库列、经过校验的制品投影和诊断信息可以为存储或传输重复事实，但必须明确其权威来源、
校验与失效规则，不能独立重新定义这些事实。

准入与恢复需要不同依赖，而不是重复的准入实现。同一策略下的所有准入来源，在语义编译前执行相同的边界校验。
恢复使用已存精确语义，不查询准入来源，也不以新的准入大小策略拒绝已有流程实例。

## 复杂度与所有权

每个抽象都应表示领域事实、能力或资源生命周期，并且只有一个明确的所有者。配置、工厂、能力提供方、运行时状态、
数据库约束和框架适配层必须保持这条所有权边界，不能为同一事实建立多套可独立配置的来源。

并发、权限、恢复和资源生命周期所需的协调必须明确存在。实现限制只有在构成公开产品契约时，才进入公共文档。

## 契约摘要

受支持的 API 应明确操作职责、无效状态处理、规范身份、时间类型、构造方式和支持等级。Durable 同样遵循这些 API 设计原则。

另见[支持面清单](supported-surfaces.md)、[版本路由](version-routing.md)和
[Durable 架构](durable-architecture.md)。
